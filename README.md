# Student CRUD API

A FastAPI application for managing students in Supabase PostgreSQL. CRUD means **Create, Read, Update, Delete**. The API validates student data, assigns IDs through the database, and returns meaningful HTTP responses.

## Endpoints

| Method | Path | Result |
|---|---|---|
| POST | `/students` | Create a student; 201 |
| GET | `/students` | List students; 200 |
| GET | `/students/{student_id}` | Fetch one student; 200 or 404 |
| PUT | `/students/{student_id}` | Replace editable fields; 200 or 404 |
| DELETE | `/students/{student_id}` | Delete one student; 200 or 404 |

## Install and configure

Requires Python 3.10+ and a Supabase project. Use a **dedicated project**, separate from the Course Enrollment assignment: both use the table name `student` but different definitions.

1. In Supabase SQL Editor, run [schema.sql](schema.sql) once. It creates one empty `student` table with database-generated IDs. If that table already exists, the script stops rather than deleting or replacing existing data.
2. From this project folder, run these commands separately:

```bash
python3 -m venv .venv
```

```bash
source .venv/bin/activate
```

```bash
python -m pip install -r requirements.txt
```

3. Fill the prepared private `.env` with your project URL and server-side **service_role key**. On a fresh clone, first copy the blank template:

```bash
cp -n .env.example .env
```

The settings are `SUPABASE_URL` and `SUPABASE_KEY`. Never put real values in GitHub, browser code, or the recording. `.gitignore` excludes `.env`; `.env.example` contains no secrets.

The SQL enables row-level security without public policies. The backend service_role key is therefore required; an anonymous key will not provide the intended database access. The application itself has no user authentication and is intended for local demonstration with fictional records, not unrestricted public deployment.

4. Start the application:

```bash
python -m uvicorn main:app --reload
```

Open [Swagger UI](http://127.0.0.1:8000/docs). Expand an endpoint, select **Try it out**, provide inputs, and click **Execute**. Stop the server with Ctrl+C. Data remains in Supabase after a restart.

`.env` is loaded from the application folder at startup. Existing exported variables take priority. Restart the server after changing configuration. Missing settings give 503, but `/docs` still opens.

## Data and validation

POST and PUT require all four editable fields:

```json
{"name":"Asha","email":"asha@example.com","age":22,"course":"Python"}
```

| Field | Rule |
|---|---|
| id | Generated by PostgreSQL; cannot be supplied in the body |
| name | String, 3–50 characters after trimming |
| email | Valid email format; mailbox ownership is not verified |
| age | JSON integer, strictly above 18 and below 100: ages 19–99 |
| course | String, 2–100 characters after trimming |

These limits follow the class example. Nulls, missing fields, unexpected fields, blank strings, invalid emails, and invalid ages return 422. Quoted ages, fractions, and booleans are rejected. Names/courses are trimmed. Duplicate email addresses are allowed because the assignment does not require uniqueness.

POST returns 201, for example:

```json
{"name":"Asha","email":"asha@example.com","age":22,"course":"Python","id":1}
```

Use the actual returned ID. GET `/students` returns an array; an empty table returns `[]`. GET `/students/1` returns one object, or 404 if absent.

PUT `/students/1` replaces all editable fields, keeping ID 1:

```json
{"name":"Asha John","email":"asha@example.com","age":23,"course":"FastAPI"}
```

An incomplete PUT returns 422. PUT does not create a missing student. Repeating an identical PUT keeps the same final record.

DELETE `/students/1` returns:

```json
{"message":"Student deleted","student_id":1}
```

A subsequent GET, PUT, or DELETE of that ID returns 404. Generated IDs may have gaps; do not assume the next ID from request counts.

Example command for creating a student:

```bash
curl -i -X POST http://127.0.0.1:8000/students -H 'Content-Type: application/json' -d '{"name":"Asha","email":"asha@example.com","age":22,"course":"Python"}'
```

For Postman, use the same routes and select **Body → raw → JSON** for POST and PUT.

## Code structure and explanations

| File | Purpose |
|---|---|
| main.py | The five routes, error handling, and logging |
| models.py | Pydantic input/output fields and validation |
| database.py | Load environment settings and provide the Supabase client |
| schema.sql | Create the student table and database access settings |
| test_api.py | Offline tests using the real SDK and simulated database HTTP responses |
| requirements.txt | Single dependency list for application and tests |

An **API** lets programs communicate. An **endpoint** is a method and path. A JSON **request body** contains student data. A **path parameter** identifies a student. FastAPI maps the route decorators to ordinary Python `def` functions; Uvicorn runs the HTTP server.

Pydantic's `BaseModel` defines a model, or named set of fields. `Field` describes limits. `EmailStr` checks email format. `Student` inherits input fields and adds the generated ID for responses. `response_model` describes and validates outgoing JSON. `model_dump()` creates a dictionary for Supabase; it is the current equivalent of the class's `.dict()`.

`database.py` follows the class's `load_dotenv`, `os.getenv`, and `create_client` approach. The client is the Python object that sends database requests. `Depends(get_client)` tells FastAPI to obtain it before calling the route. `lru_cache(maxsize=1)` reuses the constructed client. This delayed setup also lets documentation and offline tests run without real credentials.

The query pattern is the same as the class: `client.table("student")`, then `select`, `insert`, `update`, or `delete`, followed by `.execute()`. `.eq("id", student_id)` restricts an operation to one ID. `response.data` is the returned list of rows. `require_student` checks this list and returns the first row, or raises 404 for an empty list. It is reused by GET, PUT, and DELETE without a separate existence query.

The public PUT endpoint replaces all editable fields. Supabase internally sends a database PATCH request containing those fields; the public API remains PUT. Filtering the update/delete by ID prevents changes to unrelated rows.

A `try` block performs the operation; `except` catches failures. `HTTPException` produces an HTTP error response. `handle_error` preserves intentional 404 responses and maps database/network failures to 503. Unexpected failures return generic 500. The logger records operations and error types/codes without printing secret settings or raw database error details.

## Status codes

| Code | Meaning |
|---|---|
| 200 | Successful read, update, or delete |
| 201 | Student created |
| 404 | Student ID does not exist |
| 422 | Invalid input body or path parameter |
| 503 | Configuration missing, table absent, network failure, or database request failure |
| 500 | Unexpected internal application error |

## Testing and limits

```bash
python -m unittest -v test_api
```

See [VALIDATION.md](VALIDATION.md). Tests do not contact Supabase. Hosted schema setup, credentials, and permissions must be checked with the live Swagger demonstration. List responses are subject to Supabase's configured row limit; pagination is outside this small assignment. No login/JWT, PATCH endpoint, or rate-limiter is added because those features are not required.
